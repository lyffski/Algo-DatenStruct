🔬 Master-Karte: Laufzeit = Summe über alle Zeilen

\[ \begin{aligned} \Res{T(N)} &= \sum_{\text{Zeile } z} \Mem{c_z}\cdot\Idx{h_z(N)} && \text{Laufzeit = Summe über alle Zeilen: Kosten mal Häufigkeit.} \\ \Mem{c_z} &= \text{Kosten eines Durchlaufs von Zeile } z && \text{hängt vom Rechner ab (ns, Befehle).} \\ \Idx{h_z(N)} &= \text{Häufigkeit von Zeile } z && \text{hängt nur vom Algorithmus ab.} \\ \Res{T(N)} &\approx \Rule{\text{führender Term}} && \text{Für großes } N \text{ zählt nur der größte Summand.} \\ \Res{T(N)} &\in O(\dots) && \text{Die Konstante fällt weg, übrig bleibt die Wachstumsklasse.} \end{aligned} \]
\(\Res{T(N)}\)gesuchte Größe: Laufzeit (oder Anzahl einer abstrakten Operation, z.B. Array-Zugriffe) als Funktion der Eingabegröße
\(\Par{N}\)Parameter: Problemgröße (Anzahl Objekte, Tabellengröße …). In Kap. 1 zusätzlich \(\Par{M}\) = Anzahl Paare
\(\Mem{c_z}\)Kosten einer Zeile (Maschinenbefehle, ns). Hängt von Rechner und Compiler ab und ist deshalb für die Analyse egal
\(\Idx{h_z(N)}\)Häufigkeit: wie oft die Zeile läuft. Das ist die Eigenschaft des Algorithmus und steht im Tracer in der gelben Spalte
\(\Rule{\text{führender Term}}\)für großes N dominiert der größte Summand, meist die innere Schleife (Abschnitt 2.3)

📖 Vorlesen: „Die Laufzeit ist die Summe über alle Zeilen aus Kosten mal Häufigkeit. Für großes N zählt nur der am schnellsten wachsende Summand, und seine Konstante lässt die O-Notation weg.“

1.1 · Algorithmus und Datenstruktur

Von null · §1.1Warum der Algorithmus zählt, nicht der Rechner
Prüfungsaufgabe (für sich allein lösbar). Die Summe 1 + 2 + … + N soll berechnet werden. Lösung A addiert in einer Schleife, Lösung B benutzt N(N+1)/2. Wie viele Operationen braucht jede Lösung für N = 10⁹, und wie lange dauert das bei 10⁹ Operationen pro Sekunde?
Lösung von null, Schritt für Schritt
1
Algorithmus von null. Ein Algorithmus ist eine endliche, genaue Rechenvorschrift. Wie gut er ist, misst man daran, wie viele Grundoperationen er in Abhängigkeit von der Eingabegröße N braucht.
2
Lösung A. Die Schleife läuft N-mal und macht je eine Addition: 10⁹ Operationen, also etwa 1 Sekunde.
3
Lösung B. Eine Multiplikation, eine Addition, eine Division: 3 Operationen, unabhängig von N.
4
Vorgehen des Buches. Problem genau formulieren, eine einfache Lösung finden, ihre Kosten zählen, gezielt verbessern. Das zieht sich durch alle Kapitel.
\[ \begin{aligned} \text{A} &= N = 10^9 \text{ Operationen} && \text{wächst mit N.} \\ \text{B} &= 3 && \text{konstant.} \end{aligned} \]
✔ A: 10⁹ Operationen ≈ 1 s · B: 3 Operationen

Algorithmus = eine Problemlösungs-Methode, die man als Programm umsetzen kann. Sie hängt nicht von Rechner oder Sprache ab.

Datenstruktur = die Art, wie die Daten organisiert sind. Für Sedgewick ist sie ein Nebenprodukt des Algorithmus. Beides gehört zusammen.

Die 3 Zahlen, die das Kapitel motivieren:

🚀 Besserer Algorithmus: oft Faktor 10⁶ schneller.
💻 Neuer Rechner: Faktor 10–100.
🛠️ Sorgfältig statt einfach implementiert: nur Faktor 5–10, deshalb lohnt „Überoptimieren“ selten.

🎯 Prüfungsrelevant

Die Wahl des Algorithmus entscheidet über Faktoren von 100–1000 und mehr, nicht das Feintuning. Deshalb lernt man, Laufzeiten vorherzusagen, bevor man codet. Genau das ist die Analyse von Algorithmen.

1.2 · Das Beispielproblem: Konnektivität

Von null · §1.2Das Konnektivitätsproblem von Hand
Prüfungsaufgabe (für sich allein lösbar). Paare kommen einzeln an: 3-4, 4-9, 8-0, 2-3, 5-6, 2-9, 5-9. Ein Algorithmus soll ein Paar nur ausgeben, wenn es zwei bisher nicht verbundene Objekte verbindet. Welche Paare werden ausgegeben?
Lösung von null, Schritt für Schritt
1
Problem von null. Ein Paar p-q bedeutet: p und q sind verbunden. Verbundenheit ist transitiv: Aus p-q und q-r folgt p-r. Gesucht ist für jedes neue Paar die Antwort auf die Frage, ob p und q schon verbunden sind.
2
3-4, 4-9, 8-0, 2-3, 5-6. Alle neu: ausgeben. Mengen: {2,3,4,9}, {0,8}, {5,6}.
3
2-9. 2 und 9 liegen schon in derselben Menge (über 2-3-4-9): nicht ausgeben.
4
5-9. {5,6} und {2,3,4,9} sind getrennt: ausgeben. Jetzt {2,3,4,5,6,9}.
\[ \begin{aligned} \text{Ausgabe} &= 6 \text{ Paare} && \text{jedes ausgegebene Paar verringert die Zahl der Mengen um 1.} \end{aligned} \]
✔ Ausgabe 3-4, 4-9, 8-0, 2-3, 5-6, 5-9 · nicht 2-9

Die Eingabe ist eine Folge von Paaren p-q, gelesen als „p ist mit q verbunden“. Die Relation ist transitiv (p–q und q–r ergeben p–r). Das Programm soll ein Paar nur ausgeben, wenn es neu ist, also nicht schon aus den bisherigen Paaren folgt.

⚠ Zwei Stolpersteine, die oft für Fehler gehalten werden

1. " " ist kein Syntaxfehler. So steht die Zeile im Buch: Jede Ausgabezeile beginnt mit einem Leerzeichen. Wird beim Kopieren das " " verschluckt, sieht man cout << << p. Das wäre wirklich ein Kompilierfehler, weil zwischen zwei << ein Wert fehlt. Ohne führendes Leerzeichen geht auch cout << p << " " << q << endl;, Ausgabe 3␣4.

2. Warum unite statt union? union ist in C++ ein reserviertes Schlüsselwort (ein Verbund-Datentyp) und kann nicht als Funktionsname dienen. Die abstrakte Operation heißt im Buch union, die C++-Funktion heißt deshalb unite. In den Programmen 1.1–1.4 steht der union-Code direkt in der Schleife, ganz ohne Funktion.

🏗️ Das vollständige Programm (kompiliert und getestet)

Hier sind find und unite als Weighted Quick-Union mit Halbierung umgesetzt (Programm 1.4, siehe 1.3d). Für 1.2 genügt: find(p) liefert den Repräsentanten (die Wurzel), also den Namen der Menge von p. Zusätzlich gibt printComponents() am Ende die Mengen aus.

#include <iostream>   // cin, cout, endl
#include <map>        // map: Wurzel → Elemente (für die Mengen-Ausgabe)
#include <vector>     // vector: Liste der Elemente einer Menge
using namespace std;  // erlaubt cin statt std::cin

static const int N = 10;  // Objekte 0 … N−1
int id[N];                // id[i]: Elternzeiger (Wurzel: id[i] == i)
int sz[N];                // sz[i]: Knotenzahl im Baum mit Wurzel i

int find(int p)           // liefert die Wurzel = den Namen der Menge von p
{ while (p != id[p])      // solange p nicht die Wurzel ist …
    { id[p] = id[id[p]];  // … p auf seinen Großvater zeigen lassen (Halbierung)
      p = id[p];          // … und eine Stufe nach oben gehen
    }
  return p;               // p ist jetzt die Wurzel
}

void unite(int p, int q)  // vereinigt die Mengen von p und q ("union" ist reserviert)
{ int i = find(p);        // Wurzel von p
  int j = find(q);        // Wurzel von q
  if (i == j) return;     // schon dieselbe Menge: nichts zu tun
  if (sz[i] < sz[j])      // kleineren Baum unter den größeren hängen
    { id[i] = j; sz[j] += sz[i]; }
  else
    { id[j] = i; sz[i] += sz[j]; }
}

void printComponents()    // gibt jede Menge in einer Zeile aus
{ map<int, vector<int>> comp;              // Schlüssel: Wurzel, Wert: alle Elemente dieser Menge
  for (int i = 0; i < N; i++)
    comp[find(i)].push_back(i);            // Element i zur Menge seiner Wurzel legen
  int nr = 1;                              // laufende Nummer der Menge
  for (const auto& e : comp)               // e.first = Wurzel, e.second = Elemente
    { cout << "Menge " << nr++ << ": { ";
      for (int x : e.second) cout << x << " ";
      cout << "}" << endl;
    }
}

int main()
{ int p, q;                                // das gerade gelesene Paar
  for (int i = 0; i < N; i++)
    { id[i] = i; sz[i] = 1; }              // Start: jedes Objekt ist seine eigene Menge
  while (cin >> p >> q)                    // liest Paare, bis die Eingabe endet
    { if (find(p) == find(q)) continue;    // schon verbunden → nichts tun
      unite(p, q);                         // Mengen vereinigen
      cout << " " << p << " " << q << endl;  // neues Paar ausgeben (wie im Buch)
    }
  printComponents();                       // nach dem Ende der Eingabe: alle Mengen
  return 0;
}

💡 Graphentheorie-Abkürzung (§1.2, Kap. 5.4)

  
Die Paare bilden einen Graphen. Die ausgegebenen Paare bilden einen Spannbaum. Ein Baum auf N Knoten hat genau N−1 Kanten. Deshalb gilt: alle N Objekte sind verbunden ⇔ genau N−1 Paare wurden ausgegeben. Für die Ja/Nein-Frage reicht also ein Zähler.










1.3a · Quick-Find (Programm 1.1)




Von null · §1.3aQuick-Find von Hand


Prüfungsaufgabe (für sich allein lösbar). N = 5 Objekte, Paare 0-1, 1-2, 3-4. Gib id[] nach jedem Paar an (Prog 1.1). Wie viele Array-Durchläufe macht union insgesamt?


Lösung von null, Schritt für Schritt

1
Quick-Find von null. Jedes Objekt x hat im Array id einen „Namen“ id[x]. Regel: p und q sind verbunden genau dann, wenn id[p] == id[q]. find ist also ein einziger Vergleich.


2
0-1. id[0] = 0 ≠ id[1] = 1. union: Alle Einträge mit Namen 0 bekommen den Namen 1. id = 1 1 2 3 4.


3
1-2. id[1] = 1 ≠ 2: Alle mit Namen 1 bekommen Namen 2. id = 2 2 2 3 4.


4
3-4. id[3] = 3 ≠ 4: id = 2 2 2 4 4.


5
Kosten. Jede union läuft einmal durch alle N Einträge: 3 · 5 = 15 Durchläufe.


\[ \begin{aligned} \Res{T} &\ge M\cdot N && \text{Eigenschaft 1.1.} \\  &= 3\cdot 5 = 15 && \text{für dieses Beispiel.} \end{aligned} \]


✔ id = 2 2 2 4 4 · 15 Durchläufe







  
Idee und Invariante

  
Ein Array id[N] mit einem Eintrag pro Objekt. Regel: p und q sind verbunden ⇔ id[p] == id[q]. Der Wert id[x] ist also der „Name“ der Menge von x.

  
find ist ein Vergleich, also O(1) („quick find“). union muss dagegen alle Einträge mit dem alten Namen umschreiben, also O(N).

Eigenschaft 1.1

1

2

✔ id = 0 0 0 2 · sz[0] = 4 · Höhe 2







  
Idee: den kleineren Baum unter den größeren hängen

  
Ein zweites Array sz[i] speichert für jede Wurzel die Anzahl der Knoten ihres Baums. Bei union wird die Wurzel des kleineren Baums an die des größeren gehängt. So entstehen keine langen Ketten, und das kostet nur wenige Zeilen mehr.

Eigenschaft 1.3: höchstens lg N Zeiger pro find (von null bewiesen)

  
Behauptung: In einem Baum mit k Knoten ist jeder Knoten höchstens \(\lg k\) Schritte von der Wurzel entfernt.

  
Induktionsschritt: Ein Baum mit \(i\) Knoten wird unter einen mit \(j\) Knoten gehängt, wobei \(i \le j\). Die Knoten des kleinen Baums sind danach genau 1 Schritt tiefer, sitzen aber in einem Baum der Größe \(i+j\):

  
\[ \begin{aligned} \text{neue Tiefe} &= 1 + \lg i && \text{Der kleine Baum (} i \text{ Knoten) rutscht eine Ebene tiefer.} \\ &= \lg(2i) && \text{Logarithmusregel: } 1 = \lg 2. \\ &= \lg(i+i) \le \Res{\lg(i+j)} && \text{Weil } i \le j \text{, gilt die Schranke auch für den neuen Baum.} \end{aligned} \]

  
Die Tiefe wächst also nur, wenn sich die Baumgröße mindestens verdoppelt. Verdoppeln kann man sich höchstens \(\lg N\)-mal. Daraus folgt \(\Res{T \le c\cdot M \lg N}\).

Von null · §1.3dPfadkompression durch Halbierung

1
Idee von null. Während man zur Wurzel läuft, lässt man jeden zweiten Knoten auf seinen Großvater zeigen. Der Weg wird dabei etwa halb so lang, ohne zusätzliche Schleife.


2
i = 4. id[4] = id[id[4]] = id[3] = 2. Weiter bei i = 2.


3

4
Ergebnis. id = 0 0 0 2 2. Der Weg von 4 ist jetzt 4 → 2 → 0: zwei statt vier Schritte.


\[ \begin{aligned} \text{vorher} &= 4 \text{ Schritte} && \text{Kette.} \\ \text{nachher} &= 2 \text{ Schritte} && \text{halbiert.} \end{aligned} \]


✔ id = 0 0 0 2 2 · Weg von 4 halbiert






Ideal wäre es, wenn jeder Knoten direkt auf die Wurzel zeigt (wie bei Quick-Find), ohne dafür teuer umzuschreiben. Der Trick: Jeden Knoten, den find sowieso besucht, lässt man näher an die Wurzel zeigen.

for (i = p; i != id[i]; i = id[i])
  id[i] = id[id[i]];   // auf Großvater zeigen

    
Jeder besuchte Knoten überspringt einen Elternknoten, der Pfad wird ungefähr halbiert. Das Ergebnis ist asymptotisch so gut wie volle Kompression.

for (i = p; i != id[i]; i = id[i]) ;  // 1. Pass: Wurzel
for (k = p; k != i; )                  // 2. Pass: alle
  { int nx = id[k]; id[k] = i; k = nx; } //  → Wurzel

    
Ein zweiter Durchlauf setzt jeden Knoten des Pfads direkt auf die Wurzel. nx merkt sich den nächsten Knoten, bevor sein Zeiger überschrieben wird.

2.2 · Analyse von Algorithmen




Von null · §2.2Häufigkeiten aus dem Code ablesen


Prüfungsaufgabe (für sich allein lösbar). Wie oft läuft cnt++ in for (i = 0; i < N; i++) for (j = 0; j < i; j++) cnt++;? Wie oft wird die innere Bedingung geprüft? Rechne für N = 5.

1
Methode von null. Man zählt für jede Zeile, wie oft sie läuft (Häufigkeit), und multipliziert mit ihren Kosten. Die Bedingung einer Schleife läuft einmal öfter als ihr Rumpf.


2
Rumpf. Für i läuft cnt++ genau i-mal: 0 + 1 + 2 + 3 + 4 = 10.


3
Innere Bedingung. Für jedes i wird j < i genau i + 1-mal geprüft: 1 + 2 + 3 + 4 + 5 = 15.


4
Allgemein. Rumpf N(N−1)/2, Bedingung N(N+1)/2.


\[ \begin{aligned} \Res{\text{cnt}} &= \sum_{i=0}^{N-1} i = \frac{N(N-1)}{2} = 10 && \text{für N = 5.} \\ \text{Tests} &= \frac{N(N+1)}{2} = 15 && \text{einer mehr pro Runde.} \end{aligned} \]


✔ cnt = 10 · 15 Tests der inneren Bedingung

Lineare Suche und sequentielle Suche sind dasselbe Verfahren. „Sequentiell“ beschreibt das Vorgehen (eins nach dem anderen), „linear“ die Laufzeit (Θ(N)).






Sequentiell auf sortierter Tabelle (früher Abbruch)


int search(int a[], int v, int l, int r)
{ for (int i = l; i <= r; i++)      // von links nach rechts
    { if (v == a[i]) return i;       // Treffer: Position
      if (v < a[i]) return -1;       // a[i] schon größer: v kommt nicht mehr
    }
  return -1;                         // bis zum Ende nichts gefunden
}


Ohne die Zeile mit v < a[i] ist es Programm 2.1 (unsortiert): Eine erfolglose Suche muss dann immer bis zum Ende laufen.






Binär (Programm 2.2), Tabelle muss sortiert sein


int search(int a[], int v, int l, int r)
{ while (r >= l)                     // Bereich nicht leer
    { int m = (l + r) / 2;           // Mitte, abgerundet
      if (v == a[m]) return m;       // Treffer: Position
      if (v < a[m]) r = m - 1;       // links weitersuchen
      else l = m + 1;                // rechts weitersuchen
    }
  return -1;                         // Bereich leer: nicht gefunden
}


Jede Runde halbiert den Bereich: das ist Werkzeug 5 (halbieren bis 1).











Erfolgreich: die Gauß-Summe gegen die Ebenen-Summe


\[ \begin{aligned}
\text{sequentiell: } \bar C &= \frac{1 + 2 + \dots + N}{N} = \frac{N+1}{2} && \text{Position k kostet k (Gauß)} \\
\text{binär: } \bar C &= \frac{1\cdot 1 + 2\cdot 2 + 3\cdot 4 + \dots + h\cdot 2^{h-1}}{N} && \text{Ebene k: } 2^{k-1} \text{ Einträge, je k} \\
&= \frac{(h-1)\,2^h + 1}{2^h - 1} \approx h - 1 && \text{für } N = 2^h - 1 \\
&\approx \lg N - 1 && \text{die meisten liegen unten}
\end{aligned} \]






Erfolglos: wo die Unterschiede entstehen


\[ \begin{aligned}
\text{unsortiert: } \bar C &= N && \text{erst am Ende sicher} \\
\text{sortiert: } \bar C &= \frac N2 + \frac{N}{N+1} \approx \frac N2 && \text{Abbruch bei größerer Zahl} \\
\text{binär: } \bar C &= h = \lg(N+1) && \text{alle Lücken ganz unten}
\end{aligned} \]







Entscheidungsbaum der binären Suche für N = 15: woher \(\lg N - 1\) und \(\lg N\) kommen



Erfolgreich im Mittel: \((1\cdot1 + 2\cdot2 + 3\cdot4 + 4\cdot8)/15 = 49/15 \approx 3{,}27\), also etwa \(\lg 16 - 1 = 3\). Erfolglos: alle 16 Lücken liegen auf Ebene 4, also immer 4 = \(\lg 16\) Vergleiche.










Was weicht wann ab?


1Sortieren hilft der sequentiellen Suche nur bei erfolglosen Suchen (N → ≈ N/2). Erfolgreiche Suchen kosten unsortiert wie sortiert \((N+1)/2\), denn der Treffer steht im Mittel in der Mitte.


2Binär: erfolgreich ist im Mittel etwa 1 Vergleich billiger als erfolglos (\(\lg N - 1\) gegen \(\lg N\)). Ein Treffer kann schon weiter oben im Baum enden, eine erfolglose Suche läuft immer bis ganz unten.


3Wachstum: N verdoppelt → sequentiell doppelt so viele Vergleiche, binär genau einer mehr.


4Sortieren kostet selbst mindestens etwa N lg N Vergleiche (Teil 3). Es lohnt sich, wenn danach viele Suchen kommen. Und wer schon sortiert hat, sucht binär, nicht sequentiell.




\[ \begin{aligned}
M = 10^9 \text{ Suchen},\ N = 10^6 &: && c \text{ µs pro Vergleich} \\
\text{sequentiell: } M \cdot \tfrac N2 = 5\cdot 10^{14} \text{ Vergl.} &\to 5\cdot 10^{8}\,c \text{ s} \approx 16\,c \text{ Jahre} && \text{unbrauchbar} \\
\text{binär: } M \cdot (\lfloor\lg N\rfloor + 1) = 2\cdot 10^{10} \text{ Vergl.} &\to 2\cdot 10^{4}\,c \text{ s} \approx 5{,}6\,c \text{ Stunden} && \text{höchstens 20 Vergleiche pro Suche}
\end{aligned} \]

Lösung von null, Schritt für Schritt

1
Begriffe von null. Eine Garantie (worst case) gilt für jede Eingabe. Ein Mittelwert (average case) gilt nur, wenn die Eingaben zufällig verteilt sind, wie angenommen.


2
Sequentiell, worst case. Das Element steht ganz hinten oder fehlt: 10⁶ Vergleiche.


3
Sequentiell, Mittel. Bei zufälliger Position im Mittel (N+1)/2 ≈ 500 000.


4
Binär, worst case. ⌊lg 10⁶⌋ + 1 = 20 Vergleiche, für jede Eingabe: eine Garantie.


\[ \begin{aligned} \text{sequentiell} &\le N = 10^6 && \text{worst case.} \\ \text{binär} &\le 20 && \text{worst case: Garantie.} \end{aligned} \]


✔ sequentiell: 10⁶ worst, 500 000 im Mittel · binär: höchstens 20 (Garantie)







  
Worst Case → Garantie
„Nie mehr als …, egal welche Eingabe“ (Eigenschaft 2.3, 1.3). Problem: Der Worst Case kann in der Praxis nie auftreten, und gute Garantien machen Algorithmen oft komplizierter.

  
Average Case → Vorhersage
Mittelwert unter einem Eingabemodell (z.B. zufällig geordnet). Probleme: Das Modell passt vielleicht nicht, die Mathematik ist schwer, und der Mittelwert allein sagt nichts über Ausreißer.

  
Randomisiert → beides
Man mischt die Eingabe selbst zufällig (z.B. vor Quicksort). Dann stimmt das Zufallsmodell, und die Wahrscheinlichkeit für langsame Läufe ist beweisbar winzig (Quicksort, randomisierte BSTs, Hashing).

1Konstante Summe: \(\sum_{i=1}^{N} 1 = \Res{N}\) Bild: eine Reihe (Rechteck)

  

  


int cnt = 0;                      // zählt die abstrakte Operation
for (int i = 1; i <= N; i++)      // Runde i = 1, 2, …, N
  for (int k = 1; k <= M; k++)    // M fest, hängt NICHT von i ab (M = 1: keine innere Schleife)
    cnt++;                        // eine Operation

    
①Operation: cnt++. ②Summe: jede Runde liefert denselben Summanden, egal welches i.

    
\[ \begin{aligned}
    \Res{\texttt{cnt}} &= \sum_{i=1}^{N} 1 && \text{jede Runde zählt 1 (M = 1)} \\
    &= \underbrace{1 + 1 + \dots + 1}_{N \text{ Summanden}} = \Res{N} && \text{N-mal die 1 addiert} \\
    \sum_{i=1}^{N} \sum_{k=1}^{M} 1 &= \sum_{i=1}^{N} M = \Res{N \cdot M} && \text{Summand ohne i: multiplizieren erlaubt}
    \end{aligned} \]

    
Ist das die Gauß-Formel? Nein. Gauß summiert die wachsenden Zahlen \(1+2+\dots+N\) (Karte 2). Hier wird immer dieselbe Zahl 1 addiert, deshalb ist das Ergebnis einfach die Anzahl der Summanden.

1Beispiel ① (leicht): alle Paare i < j

  

  
① Operation: cnt++ (Zeile 3).

  
② Für festes i läuft j von i+1 bis N−1, also \(N-1-i\) Durchläufe:

  
\[ \Res{\texttt{cnt}} = \sum_{i=0}^{N-1} (N-1-i) = \underbrace{(N-1)}_{i=0} + \underbrace{(N-2)}_{i=1} + \dots + \underbrace{0}_{i=N-1} \]

  
③ Das ist die Summe 0+1+…+(N−1), also Formel 2.1 um eins verschoben: \(\Res{\frac{N(N-1)}{2}}\).

  
④ Führender Term \(\frac{N^2}{2}\). Verdopplung ergibt ×4.

  Verdict: Θ(N²), ungefähr N²/2. So sieht jeder „vergleiche jedes Paar“-Algorithmus aus (z.B. die elementaren Sortierer in Teil 3).





  
2Beispiel ② (mittel, mit Falle): die äußere Schleife halbiert

  

  
① Operation: cnt++.

  
② i nimmt die Werte N, N/2, N/4, …, 1 an. Die innere Schleife läuft jeweils i-mal:

  
\[ \Res{\texttt{cnt}} = \underbrace{N}_{i=N} + \underbrace{\tfrac N2}_{i=N/2} + \underbrace{\tfrac N4}_{} + \dots + \underbrace{1}_{i=1} \]

  
③ Geometrische Reihe, wie bei Formel 2.3: \(N(1+\frac12+\frac14+\dots) < \Res{2N}\).

  
④ Falle: Es sind zwei Schleifen, und die äußere läuft lg N-mal, also tippt man auf N lg N. Weil die innere aber mitschrumpft, ist es nur linear.

  Verdict: Θ(N), unter 2N. Nicht einfach „Schleifen multiplizieren“, sondern immer summieren.





  
3Beispiel ③ (schwer): die innere Schrittweite wächst mit i

  

  
① Operation: cnt++.

  
② j läuft von i bis N in Schritten von i, also \(\lfloor N/i\rfloor\)-mal:

  
\[ \begin{aligned} \Res{\texttt{cnt}} &= \sum_{i=1}^{N} \left\lfloor \frac Ni \right\rfloor && \text{Für jedes } i \text{ läuft } j \text{ genau } \lfloor N/i\rfloor\text{-mal.} \\ &\approx N\left(1+\tfrac12+\tfrac13+\dots+\tfrac1N\right) && N \text{ ausklammern.} \\ &= N\,H_N && \text{Die Klammer ist die harmonische Zahl (Abschnitt 2.3).} \end{aligned} \]

  
③ \(H_N\approx \ln N+\gamma\), also \(\Res{\texttt{cnt}\approx N\ln N}\).

  
④ Verdopplung: etwas mehr als ×2.

  Verdict: Θ(N log N), ungefähr N ln N ≈ 0,69 N lg N. Die harmonischen Zahlen tauchen direkt im Code auf.
